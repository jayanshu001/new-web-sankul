# Report Exports — Architecture (CSV / Excel)

How every admin **report export** works, so any developer can extend or debug one.
Covers the 6 reports: Subscription, Test Series, Live Course, Ebook, Book Orders, Referral.

Last updated: 2026-07-10.

---

## TL;DR

- Each report has **two delivery paths that share one builder**:
  1. **Sync** — `GET /admin/.../export/csv` and `/export/excel`. Simple, but the whole file
     is built while the HTTP request is held open → the gateway 504s after ~60s. Fine for
     small pulls only.
  2. **Async job** — `POST /admin/exports {type, format, filters}` → returns a `jobId`
     immediately; a BullMQ worker builds the file off-request, uploads it to Spaces
     (private), and `GET /admin/exports/:jobId` polls until a signed download URL is ready.
     **This is the path for large / lakhs-of-rows exports** (no request held open → no 504).
- **One builder per report** feeds both paths, so async output is **byte-identical** to sync.
- Every builder is **uncapped + streamed**: keyset pagination (id DESC, batches of 5,000,
  no `OFFSET`) + `ExcelJS.stream.xlsx.WorkbookWriter` (XLSX) / `fast-csv` (CSV) → memory
  stays bounded no matter the row count. There is **no 100k cap** anymore.
- **CSV** is generated by the `fast-csv` package via the shared helper
  `src/utils/csvExport.ts` → `buildCsvFromRowBatches(headers, asyncRowBatches)` (RFC-4180
  quoting). **XLSX** uses `ExcelJS` (fast-csv is CSV-only).
- **Dates** in every export render as **IST** `YYYY-MM-DD HH:mm:ss` (e.g. `2026-10-06 00:01:21`).
- **Date-range filter** on every report is `createdFrom`/`createdTo` → `createdAt`, bounded
  at **IST day edges** (`00:00:00.000` / `23:59:59.999` `+05:30`). Legacy param names still work.

## The two paths

```
Sync:   FE ──GET /export/csv──▶ controller ──▶ report.buildXxxCsv(query) ──▶ res.send(file)
                                                       │ (same builder)
Async:  FE ──POST /admin/exports──▶ export-job ──enqueue──▶ BullMQ worker
           ◀──jobId──                                          │
        FE ──GET /admin/exports/:jobId (poll)──▶ status        ├─ registry[type].build(filters, fmt)
           ◀──signed Spaces URL when ready──                   ├─ upload to Spaces (private)
        FE ──download from signed URL──▶ file                  └─ mark row ready
```

- Async subsystem lives in `src/modules/export-job/` (registry, service, repository) +
  `src/admin/exports/` (routes, controller, scheduler). Table: `ws_export_job` (model
  `ExportJob`). See [`EXPORT_JOBS_ADMIN.md`](./EXPORT_JOBS_ADMIN.md) for the job API/flow.
- The **registry** (`export-job.registry.ts`) maps each `type` to that report's **existing
  sync parser + builder** — nothing report-specific is re-implemented for async.

| `type` | Report | Filename base | Formats |
|---|---|---|---|
| `subscription` | Course/Package Subscriptions | `subscription-report` | csv, excel |
| `testSeriesSub` | Test Series Subscriptions | `test-series-subscriptions` | csv, excel |
| `liveCourseSub` | Live Course Subscriptions | `live-course-subscriptions` | csv, excel |
| `ebookSubscription` | Ebook Subscriptions | `ebook-subscriptions` | csv, excel |

## The shared builder pattern (uncapped + streamed)

Every builder follows this shape (reference: `modules/admin-subscription/admin-subscription.service.ts`):

**1. Repository — keyset page (no `OFFSET`, no cap):**

```ts
// walk the whole filtered set in id-DESC pages; each page is O(take) on the PK index
listXxxPageKeyset: (where, beforeId: number | undefined, take: number) =>
  prisma.xxx.findMany({
    where: beforeId ? { AND: [where, { id: { lt: beforeId } }] } : where,
    orderBy: { id: "desc" },
    take,
  }),
```

**2. Service — async iterator over batches, then stream to CSV/XLSX:**

```ts
const EXPORT_BATCH = 5000;

async function* iterateExportRows(query, now) {
  let beforeId;
  for (;;) {
    const rows = await repo.listXxxPageKeyset(where, beforeId, EXPORT_BATCH);
    if (!rows.length) break;
    yield await hydrate(rows, now);              // resolve related maps per batch
    if (rows.length < EXPORT_BATCH) break;
    beforeId = rows[rows.length - 1].id;
  }
}

// XLSX: streaming workbook writer → PassThrough → Buffer (worksheet never held in memory)
const wb = new ExcelJS.stream.xlsx.WorkbookWriter({ stream: pass, useStyles: false, useSharedStrings: false });
for await (const batch of iterateExportRows(query, now))
  for (const r of batch) ws.addRow(COLUMNS.map(c => c.get(r))).commit();
```

Why keyset, not `OFFSET`: deep `OFFSET` on lakhs of rows is O(n²) (each page re-scans). Keyset
(`WHERE id < :beforeId ORDER BY id DESC`) is O(take) per page on the primary key.

**Export ordering is `id DESC`** (≈ newest-first / `createdAt DESC`). A custom `sortBy` sorts
the on-screen list but **not** the export file (keyset needs a stable key).

## Date & filter contract (all reports)

- **Export cell format** — IST `YYYY-MM-DD HH:mm:ss`. Helper (in each service):

  ```ts
  const IST_OFFSET_MS = 330 * 60_000; // Asia/Kolkata, no DST
  const fmtExportDate = (d) => {
    const t = new Date(d); if (!d || isNaN(t)) return "";
    const s = new Date(t.getTime() + IST_OFFSET_MS);
    return `${s.getUTCFullYear()}-${pad(s.getUTCMonth()+1)}-${pad(s.getUTCDate())} `
         + `${pad(s.getUTCHours())}:${pad(s.getUTCMinutes())}:${pad(s.getUTCSeconds())}`;
  };
  ```

- **Filter** — `createdFrom` / `createdTo` (`YYYY-MM-DD`) → `createdAt`, bounded at IST day
  edges so the admin's calendar pick includes the full IST day:

  ```ts
  // from → ...T00:00:00.000+05:30 ; to → ...T23:59:59.999+05:30
  const parseDayBound = (v, end) =>
    /^\d{4}-\d{2}-\d{2}$/.test(v) ? new Date(`${v}T${end ? "23:59:59.999" : "00:00:00.000"}+05:30`) : new Date(v);
  ```

  Legacy aliases still accepted: `dateFrom`/`dateTo` (subscription, TS, live, ebook, book) and
  `fromDate`/`toDate` (referral). A naive UTC/local parse (the old bug) dropped the last 5.5h.

## Enabling the async path (ops + FE)

The backend is ready; the async path only actually runs when:

1. **FE flag** `VITE_ASYNC_EXPORTS=true` in the prod build (build-time, baked into the bundle).
   Off → FE uses the sync endpoints → large data 504s.
2. **FE support set** — the report's `type` must be in `ASYNC_SUPPORTED_TYPES` (`exports.service.ts`).
   All 6 are included as of 2026-07-10.
3. **Server** — the `report-export` BullMQ worker running + Redis up, or jobs are created but
   never complete.
4. **DDL** — `ws_export_job` table applied (`docs/migration/schema-changes/2026-07-09_export_job.sql`).

Deploy order: DDL → backend (worker + Redis) → `VITE_ASYNC_EXPORTS=true`.

Notes: Referral async is **CSV-only** (the job throws on `excel`). The client poll deadline is
`MAX_POLL_MS` (30 min) — matched to lakhs-row generation time.

## Adding a new report export

1. In the report's module service, add `buildXxxCsv` / `buildXxxXlsx` following the shared
   pattern above (repo `listXxxPageKeyset` + streamed builders; IST dates; `createdFrom/To`).
2. Export the controller param-parser (`Record<string,string>` → typed query).
3. Add one entry to `REGISTRY` in `export-job.registry.ts` (`filenameBase` + `build`).
4. Add the `type` to the FE `ASYNC_SUPPORTED_TYPES`.
5. `yarn typecheck`, and log the change in `docs/MIGRATION_QUERY_CHANGES.md`.
